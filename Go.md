1. Packages and exported vs. unexported names

Every file starts with package X. Files in the same directory with the same package name share everything declared in them — no imports needed between them. That's why employment_type_events.go and employee.go are both package service and can call each other's functions directly.

The capitalization rule is the whole story for visibility: a name starting with a capital letter is exported (public, usable from other packages); lowercase is unexported (private to the package). No public/private keywords like Java/TS — just the first letter.

- PublishPayload (capital P) — exported, part of SNSPublisher's public interface, callable from any package.
- publishEmploymentTypeChangeEvent (lowercase p) — unexported, only callable from within package service. This is exactly why its test has to live in the same package/directory, as we covered.

2. Structs + methods = Go's "objects"

Go has no classes. Instead: a struct holds data, and you attach functions to it as "methods" using a receiver:

```go
type employeeService struct {
    repo         repository.EmployeeRepository
    snsPublisher sns.SNSPublisher
    logger       *logger.Logger
}

func (s *employeeService) LogEmploymentTypeChange(ctx context.Context, ...) (...) {
    // `s` is the receiver — like `this`/`self` in other languages
}
```


(s \*employeeService) between func and the method name is the receiver — it says "this function is a method on \*employeeService, accessible as s inside." That's why inside LogEmploymentTypeChange you'll write s.snsPublisher, s.logger — s is just the instance.

3. Pointers (* and &)

\*employeeService means "pointer to an employeeService" — a reference, not a copy. You'll see this constantly:

- \*model.EmploymentTypeHistory — a pointer to that struct. Functions return pointers instead of values so (a) it's cheap (no copying a big struct) and (b) nil can represent "no result" — Go doesn't have null, but a pointer's zero value is nil.
- In the helper you're about to write, the history parameter is \*model.EmploymentTypeHistory — you access its fields exactly like a normal struct, history.EmployeeID, history.EmploymentType — Go automatically dereferences for field access, no -> needed like C.

4. No exceptions — errors are just return values

Go functions that can fail return two values: the result, and an error. There's no try/catch. The universal pattern:

result, err := someFunc()
if err != nil {
    return err  // or handle it
}
// use result — guaranteed no error past this point

You'll see this exact shape everywhere in employee.go. error is just an interface — nil means "no error." The codebase defines its own sentinel errors as package-level variables (ErrEmployeeNotFound = errors.New("employee not found") in employee.go), and checks them with errors.Is(err, service.ErrEmployeeNotFound).

Your helper, publishEmploymentTypeChangeEvent, deliberately has no return value at all (not even error) — that's the concrete expression of "log and continue": there's nothing for the caller to check, because failure is fully absorbed inside the function.

5. Interfaces are satisfied implicitly

type SNSPublisher interface {
    PublishPayload(ctx context.Context, payload any) error
}

Any type that happens to have a method with that exact signature automatically "implements" SNSPublisher — there's no implements keyword, no declared relationship. snsPublisher (the real AWS-backed one) and MockSNSPublisher (generated by mockery for tests) both just happen to have a PublishPayload method, so both can be passed anywhere an SNSPublisher is expected. This is why your helper's signature takes publisher sns.SNSPublisher as a parameter — in production it gets the real one, in tests it gets the mock, and the function itself doesn't know or care which.

6. context.Context — the first parameter you'll always see

ctx context.Context shows up as the first argument almost everywhere (LogEmploymentTypeChange(ctx context.Context, ...)). It carries request-scoped stuff — cancellation signals, deadlines, tracing IDs — through a whole call chain. For your purposes right now: just thread it through, pass the same ctx you received into whatever you call (publisher.PublishPayload(ctx, payload)). You don't need to construct one yourself except in tests (context.Background()).

7. Struct tags — how Go structs map to JSON
```go
type EmploymentTypeChangeRecord struct {
    EmployeeID     int    `json:"employee_id"`
    EmploymentType string `json:"employment_type"`
}

```

The backtick string after each field is a struct tag — metadata read by the encoding/json package. It says "when you marshal this struct to JSON, call this field employee_id," even though the Go field name is EmployeeID (capitalized, because it needs to be exported for json.Marshal to see it at all — unexported fields are invisible to reflection-based packages like encoding/json).
