# Overview 
- `generateLargeArray`: fills a `vector<int>` of length `size` with `rand() % max_value`, so each element is in `[0, max_value)`.
- `my_sort`: **bubble sort**. The inner loop compares adjacent pairs and swaps if out of order; the bound `n - i - 1` shrinks each pass because after pass `i`, the `i` largest elements have "bubbled" to their final positions at the tail. Ascending order.
- `main`: generates a 10,000-element array, sorts it, prints the last 5 (i.e. the 5 largest).

## Array size scaling 
Wrote a bash script to measure how the change in the Array size affected the user time, real time and the system time. The system time is mostly constant across the runs since it is single threaded with no context switch overhead. The user time grows quadratically since the time complexity of the Bubble sort is O(n^2).

## Max value scaling 
Increasing the max possible random value did not significantly increase the user time. Other than the jump between max_value = 10 to max_value = 100. This is because the number of swaps between values is small when the max value is small.

# Optimisation 
```
std::sort(largeArray.begin(), largeArray.end());
```
Utilised standard library sort instead of the bubble sort. Theoretical time complexity of std::sort is O(nlogn).  

Unlike bubble sort, where real ≈ user (sort dominated runtime), std::sort shows real > user by ~50% at n=50000. 
The sort is now so fast that whole-process time is dominated by array generation and process overhead rather than the sort itself. 
`/usr/bin/time` — appropriate for the multi-second bubble sort — lacks the resolution and isolation to measure std::sort cleanly at these sizes.
